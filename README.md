 ## 1. 项目简介
&emsp;&emsp;本项目围绕应用故障智能化排障，构建了从日志采集、模板提取、频次异常检测、告警降噪聚合到指标级根因定位的全链路智能运维闭环

&emsp;&emsp;基于 ELK 与 Drain3 实现日志模板化抽象，采用 MAD 算法替代传统 Z-Score 实现日志频次异常检测，通过三级降噪机制有效控制误报率；联动 Prometheus 时序监控体系，基于动态回溯窗口与基线分离策略实现跨维度根因定位；集成本地大语言模型 Qwen2.5-1.5B 自动生成排障建议，形成（日志 + 指标）双维度可观测性体系与（检测→定位→诊断建议）的智能化闭环

### 1.1 **技术栈**
**日志采集与存储链路**

- Filebeat：业务日志文件实时采集、上报

- Elasticsearch：日志数据持久化存储与检索

- Kibana：日志可视化检索、索引管理

- Drain3：日志模板自动聚类、动态参数占位符提取

**指标监控链路**

- Prometheus：时序指标存储与 PromQL 查询

- Grafana：监控大盘可视化

- node-exporter：服务器 CPU、内存、磁盘、网络指标采集

- mysql-exporter：MySQL 慢查询、连接池、InnoDB 运行指标采集

**智能诊断层**

- Python 主程序：日志聚合、异常窗口切割、指标关联分析

- MAD 中位数绝对偏差算法：时序异常检测、修正 Z-Score 打分

- Ollama + Qwen2.5:1.5b：本地私有化大模型，输出故障根因与排查建议

**告警推送层**

钉钉自定义机器人 WebHook：告警文本 + AI 诊断结果一键推送告警群 

### 1.2 核心技术亮点
**1. 日志模板化抽象**

通过 Drain3 在线聚类算法对非结构化日志做模板提取，将用户 ID、IP、耗时等动态变量统一标记为 <*>，实现日志从文本到结构化模板的降维抽象，大幅降低后续异常检测的计算开销

**2. MAD 异常检测替代传统 Z-Score**

针对运维日志尖峰多、分布非正态的特点，采用中位数绝对偏差算法计算异常得分，相比均值 Z-Score 对极端离群点鲁棒性更强，避免少量峰值拉高基线导致的漏检问题

**3. 三级告警降噪机制**

一级降噪：模板聚类合并同类日志，避免同一故障多条重复日志触发重复告警

二级降噪：持续时长阈值过滤，剔除瞬时抖动类单点异常

三级降噪：指标联动校验，日志异常需匹配对应时段指标波动，否则判定为低风险日志事件

**4. 动态回溯窗口 + 基线分离策略**

打破固定巡检窗口限制，根据日志异常爆发时段自动回溯构造指标查询窗口，将历史基线区间与检测区间分离计算，确保基线数据不受当前故障污染，根因定位更精准

**5. 本地化大模型闭环诊断**

全流程私有化部署，无需调用公网大模型接口；将日志模板、异常时段、指标异常得分结构化拼接为 Prompt，输出标准化根因结论与可执行排查步骤，形成可观测到诊断的完整闭环

### 2.2 架构说明
**1. 日志采集层**   

    负责全量日志的采集、清洗与存储：

- Filebeat 挂载应用日志目录，实时增量采集日志文件，支持多行日志合并、字段提取、日志过滤、时间标签挂载

- Elasticsearch 作为日志存储引擎，提供全文检索、时序区间查询，支撑故障时段的历史日志回溯

- Kibana 提供可视化检索界面，支持日志查询、过滤与趋势分析

**2. 日志解析与特征提取层**  

    将非结构化原始日志完成结构化处理，产出异常检测所需时序特征：

- 定时从 Elasticsearch 拉取指定时间窗口的日志数据

- 基于 Drain3 在线日志聚类算法自动提取日志模板，区分固定文本与动态变量，变量统一使用<*>占位；日志模板持久保存，实现后续日志的快速匹配归类

- 按分钟粒度统计每个日志模板的出现次数，生成模板 - 时间频次矩阵，作为异常检测的输入数据源

**3. 异常检测层**  

    独立封装的统计检测微服务：

- 基于 FastAPI 构建，提供/detect/log接口，接收日志模板频次时序数据

- 核心算法采用 MAD（中位数绝对偏差）异常检测算法，对比传统 Z‑Score，不受极端峰值干扰，针对日志突增场景拥有更强抗干扰能力

- 内置 Bearer‑Token 接口鉴权、时序数据长度校验、空值清洗；返回异常下标、触发时刻、频次、异常偏离得分

**4.告警降噪与根因分析层**  

&ensp;&ensp;&ensp;**告警降噪模块：** 
- 根据日志模板 ID 进行分组，采用时间窗口合并策略：相邻异常间隔小于合并阈值则合并为一条完整故障事件，间隔超出阈值则拆分为独立告警事件

- 配置最小异常持续时长阈值，过滤瞬时单点抖动产生的无效毛刺告警，降低整体误报

- 自动计算每一次故障事件准确的开始、结束时间，防止告警窗口无限扩张

&ensp;&ensp;&ensp;**根因分析模块：** 
- 双模式巡检策略：动态窗口巡检跟随故障时间，拆分异常前基线区间、故障检测区间；固定兜底巡检读取最近 N(默认 5 min) 分钟指标，作为时序查询失败的降级方案

- 请求 Prometheus 获取 CPU、内存、慢查询、数据库连接等关联监控指标；执行空值清洗、95分位数封顶、分数上限、异常涨跌方向判定、得分去重排序，输出 Top3 可疑根因

**5. AI 智能诊断中心**

    平台私有化本地故障推理模块，承接日志告警与指标根因结果，完成智能化故障研判：

- 基于 Ollama 本地部署 Qwen2.5‑1.5B 大模型，全程内网推理，不需要调用公有大模型接口，保障运维数据安全

- 内置运维故障提示词模板、故障处置知识库，支持 RAG 检索历史同类告警案例

- 接收告警时段、异常日志模板、峰值频次、指标异常得分、Top‑3 可疑指标等结构化数据

- 自动输出故障根本原因、分步排查操作、告警紧急等级、后续系统优化建议

**6. 通知分发层**  

    统一告警出口：

- 通过钉钉加签机器人推送 Markdown 格式告警消息

- 告警消息包含异常日志模板ID、异常时段、峰值频次、双维度 Top‑3 根因排名以及 AI 生成的全套诊断方案

- 附带 Kibana 日志检索链接、Grafana 监控大盘的直达链接，支持一键跳转页面排查

## 5. Drain 算法
&ensp;&ensp;Drain（Drain: An Online Log Parsing Approach with Fixed Depth Tree）是基于固定深度前缀树的在线日志模板挖掘算法，核心思路：将日志文本分词后构建一棵固定深度的前缀树，通过逐层匹配 + 最终相似度计算，将结构相似、仅动态参数不同的日志归为同一簇，自动提炼标准化日志模板

&ensp;&ensp;它是工业界最主流的无监督日志解析算法，广泛应用于运维日志降噪、异常检测、根因定位场景
### Drain 算法执行流程图
### 5.1 整体业务流程
```
原始日志文本
    |
    ↓
【预处理阶段】
正则剥离固定内容（时间、级别、进程号） → 提取日志正文
    |
    ↓
【分词阶段】
按空格/分隔符拆分日志为 Token 序列（单词+数字+符号），变量替换为<*>
    |
    ↓
【前缀树检索阶段】   
从树根开始          ─► 先按 token 序列总长度分流 
    |
    ├── 存在匹配路径 ─► 到达叶子节点

    |

相似度 ≥ 阈值 ？─► 是 ─► 归入已有模板簇，更新模板
    |         |

    ↓
【输出结果】

```

##  6. 告警降噪与根因分析机制
### 6.1 告警降噪：时间窗口聚合规则
- **合并窗口**：默认 5 分钟(自定义)，相邻异常点时间差 < 合并窗口则归为同一故障事件

- **拆分条件**：时间差 ≥ 合并窗口时拆分为两个独立告警事件，避免无限拉长

- **毛刺过滤**：最小持续时长（默认1分钟），持续时间不足的孤立单点直接过滤，不推送告警

- **设计原则**：采用严格边界切割策略，保证间隔等于窗口时一定拆分，杜绝周期性告警永久合并的问题；每个聚合事件时长可控，与根因回溯窗口完美配合

- **效果**：将离散异常点聚合为可解读的故障事件，大幅减少告警数量，杜绝同一故障重复推送

### 6.2 根因分析动态窗口机制
根因分析围绕三个关键窗口展开，所有时间均为消除时区的 datetime 对象

| 窗口名称|含义| 取值逻辑|
|----------|------|----------|
| **合并窗口** (TIME_WINDOW_MINUTES) | 告警聚合时间粒度，决定单个故障事件的边界 | 配置项，默认 5 分钟 |
| **回溯窗口**  | 用于计算指标正常中位数与 MAD 的平稳数据区间，长度 ≥ 1 倍合并窗口 | 异常开始时间前 N 分钟，确保基线无异常污染 |
| **巡检窗口** (查询窗口 query_window) | 单次根因分析从 Prometheus 拉取指标的实际时间范围，长度 = 回溯窗口 + 合并窗口 | 由 `build_query_window` 动态计算：起点 = 异常开始 - lookback_before，终点 = 异常结束 + lookback_after，并额外拓宽 3 分钟规避 Prometheus 离散求值边界空洞 |
| **基线窗口** |(query_window["lookback_before"]*0.7) / total_span|基线最高只允许占巡检总窗口70%，强制留存30%作为检测区间 |
---

**窗口关系可视化**：
```
x 代表异常发生时间

合并窗口: 
——————————
|       x|
——————————
异常正好发生在合并窗口末尾: 
两个异常发生的时间差 >= 合并窗口 则分为俩个独立的告警事件
发生在合并窗口末尾的异常点视为下一个合并窗口的起点，为一个独立的告警事件
回溯窗口 >= 1 * 合并窗口
巡检窗口 >= 2 * 合并窗口
巡检窗口 = 回溯窗口 + 合并窗口

——————————
|x       x|
——————————
异常正好发生在合并窗口起点 | 异常发生在合并窗口末尾（不包含末尾）: 
回溯窗口 = 合并窗口
巡检窗口 = 合并窗口
巡检窗口 = 回溯窗口 = 合并窗口
```
**总结**：
查询窗口=巡检窗口=回溯窗口（基线窗口+检测窗口）+后置的恢复窗口

**窗口设计约束**
- `lookback_before` ≥ 2 × 合并窗口，保证基线数据覆盖至少一个完整聚合周期

- `lookback_after` ≥ 2 × 最小持续异常时长，覆盖恢复验证

- 巡检窗口 = 基线窗口（前 N 分钟） + 异常持续时段 + 后观察段，各段均有余量，确保 MAD 评分稳定可靠

- 所有窗口均动态跟随异常事件的实际时间，而非固定时间切片，避免数据空洞

- 边界切割严格：diff >= TIME_WINDOW_MINUTES 保证间隔正好等于窗口时一定拆分为两次独立故障，不粘连

- 与回溯窗口完美配合：每个聚合事件的时长 < 窗口大小， lookback_before = 2 * TIME_WINDOW_MINUTES 可以覆盖完整故障链路，不会出现数据截断

- 避免事件无限拉长：如果用 >，持续周期性告警（每 5 分钟一次）会永远合并在同一个事件里，失去降噪意义

### 6.3 双模式根因巡检机制
**模式一：动态异常根因巡检**

- 触发时机：检测到日志异常事件时自动触发

- 时间范围：以异常事件的起止时间为核心，向前拓展回溯窗口、向后拓展恢复窗口进行观察，动态生成巡检区间

- 分析目标：定位本次日志异常对应的系统指标根因，回溯故障发生时刻的指标异动

- 输出结果：动态根因 Top3 排名，标注异常时段与异常方向

**模式二：固定近实时根因巡检**

- 触发时机：无论是否检测到日志异常，每次调度执行时固定运行

- 时间范围：固定最近 N （默认5）分钟窗口，做全量关联指标的异常巡检

- 分析目标：覆盖无日志异常但指标已出现异动的场景，补充日志检测的盲区，实现近实时性能巡检

- 输出结果：固定窗口根因 Top3 排名，标注巡检时间范围

### 6.4 根因打分机制
- 基础得分：对每个关联指标，用基线窗口数据计算中位数和 MAD，再计算检测窗口内各点的修正 z-score

- 去毛刺：采用95分位数替代最大值作为峰值得分，避免极端单点拉高分数

- 分数封顶：设置最高得分上限（默认25σ），解决稳态指标因基线 MAD 极小造成的得分爆炸

- 方向判定：以前70%基线数据与后30%检测数据的均值对比，确定指标异常方向（↑/↓）

- 去重排序：同名指标去重保留最高分，双维度按得分降序分别输出 Top3 可疑根因

### 7.1简化一键调优速查表
| 使用场景 | 核心目标 | 关键参数调整 | 口诀备注 |
|----------|----------|--------------|----------|
| 测试压测 | 高灵敏度、全量捕获异常 | MIN_SCORE_THRESHOLD=0.5，MIN_CONT_POINTS=2 | 宁可错杀，不可放过 |
| 生产稳定环境 | 强降噪、降低误告警 | MIN_ANOMALY_DURATION=2，MIN_CONT_POINTS=5 | 精准报警，拒绝骚扰 |
| 微服务异步链路 | 适配故障传导滞后 | TIME_WINDOW_MINUTES=10‑15，PROPAGATION_DELAY_MIN=3‑5 | 等一等，再下结论 |

### 7.2场景化一键调优策略
**1. 测试压测场景（高灵敏度、全量捕获）**

降低准入门槛、放大告警能力，验证全链路可用性**

- MIN_SCORE_THRESHOLD=0.5、MIN_CONT_POINTS=2–3

- LOOKBACK_MINUTES=60、TIME_WINDOW_MINUTES=3–5

- GLOBAL_MAX_SCORE=25、MIN_RELATIVE_MAD=0.05

- SCRAPE_INTERVAL_SEC=15、PROM_QUERY_STEP_SEC=15

**2. 生产稳定场景（强降噪、低误报）**

抑制抖动、过滤毛刺，保障告警精准度

- MIN_ANOMALY_DURATION=2–3、MIN_CONT_POINTS=5–6

- MIN_SCORE_THRESHOLD=1.5–2.0、TIME_WINDOW_MINUTES=5–10

- MIN_RELATIVE_MAD=0.1–0.2、GLOBAL_MAX_SCORE=30–50

- SCRAPE_INTERVAL_SEC=30、PROM_QUERY_STEP_SEC=30

**3. 微服务多依赖/异步链路场景（适配故障滞后传导）**

适配链路长、故障传导慢、数据延迟高的特点

- TIME_WINDOW_MINUTES=10–15

- PROPAGATION_DELAY_MIN=3–5

- MIN_CONT_POINTS=5–6

## 10. 后续拓展优化方向
### 10.1 告警降噪能力升级

在现有时间窗口聚合的基础上，构建多重降噪策略：

- **文本语义聚类**：引入TF-IDF + 余弦相似度，对告警文本进行二次聚合，过滤因日志变量参数差异（如不同IP、用户ID）引发的同类告警重复推送

- **拓扑传播抑制**：构建微服务调用依赖拓扑，实现故障传播告警抑制——上游服务触发告警后，自动屏蔽下游衍生告警，从源头杜绝告警风暴

- **分级与静默策略**：实现多级告警分级（提示、一般、严重、紧急），支持运维窗口变更静默、夜间低优先级告警屏蔽，配合频率阈值与抖动过滤，有效控制无效告警干扰

### 10.2 根因分析能力增强

- **多维关联定位**：梳理服务调用链路拓扑，依照故障传播延迟权重优化根因得分排序；接入OpenTelemetry链路追踪、进程状态、网络等更多维数据源，将定位能力从“日志+指标”升级为多维度关联根因分析

- **故障知识库与LLM深度优化**：搭建结构化故障案例知识库，保存历史故障、异常日志与处理方案，利用历史案例对MAD根因得分进行加权修正；深度优化本地大模型诊断逻辑，精简提示词、约束结构化输出格式，自动生成包含故障解释、风险等级与分步排障方案的高质量诊断建议

- **置信度评分**：增加根因置信度打分机制，区分强关联与弱关联指标，辅助运维人员优先排查高可疑组件

### 10.3 架构与工程优化

- **统一API网关**：搭建AIOps统一API-Gateway，聚合日志解析、MAD异常检测、告警降噪、根因分析及大模型诊断接口，对外提供标准化调用入口

- **可观测性三支柱落地**：完整落地日志（ELK）、指标（Prometheus）、链路追踪（OpenTelemetry）三大可观测性支柱，实现全链路故障追踪

- **性能与调度优化**：重构定时巡检调度模块，支持多业务日志任务并行解析与异步任务队列；优化MAD算法基线缓存、ES批量查询与Prometheus时序请求逻辑，降低中间件查询压力

- **可视化运维中心**：开发简易前端可视化面板，集中展示日志模板、异常事件列表、根因排行、历史故障台账及钉钉告警记录，打造一站式智能运维诊断中心

### 10.4 自动化运维闭环拓展

- **多渠道分级通知**：完善邮件、钉钉等多渠道告警推送，支持不同故障等级对应不同通知方式，确保高优故障及时触达
