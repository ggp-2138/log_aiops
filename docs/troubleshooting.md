| 坑点 | 现象 | 根因 | 解决方案 |
|------|------|------|----------|
| **时间类型混用导致查询窗口偏移** | 打印时间字符串显示正常（如 15:50），但 Prometheus 查询返回数据为空，`baseline_points` 和 `detect_points` 全为 0，所有指标被 SKIP | ES 日志时间带时区（Asia/Shanghai），代码中 `datetime.now()` 返回 naive datetime，两者混用时 `.timestamp()` 计算规则不同：带时区正确减 8 小时转 UTC，naive 被直接当成本地时间，导致实际查询窗口跑到了未来 | 统一所有时间为 UTC 带时区：编写 `normalize_datetime` 函数将任何输入转为 UTC datetime；所有 `datetime.now()` 改为 `datetime.now(timezone.utc)`；跨模块时间类型不一致是运维开发高频故障，必须规范化 |
| **Prometheus range 查询离散求值导致空结果** | 动态窗口内原始数据确实存在，但 `query_range` 返回空数组，打印出的时间区间看似有数据却查不到；早期测试使用固定历史时间，而 Prometheus 在该时间段内可能无数据 | Prometheus 范围查询按 `start + n*step` 离散求值，并非直觉上的连续取数；每个求值点仅向前回溯默认 5 分钟寻找样本；窗口起始点对齐整点时恰好落入采集空洞，首个求值点无样本导致整条时序返回空 | 查询时窗口前后各拓宽 3 分钟规避边界对齐问题；理解 Prometheus 离散求值、lookback-delta 机制，不能仅凭时间区间直觉判断数据是否存在；最终采用动态窗口跟随异常时间自然对齐 |
| **有状态容器无持久化导致历史数据丢失** | 长跨度历史窗口（如 24 小时）查询无数据，但近实时窗口（如 5 分钟）正常；Prometheus 重启后所有历史指标清零 | Docker 部署的 Prometheus 未挂载数据持久卷，容器重启后时序数据全部清空，仅重启后新采集数据可用 | 为 Prometheus 等有状态服务挂载持久卷（volumes）；重启丢数据会直接导致回溯分析、基线对比等依赖历史数据的功能完全失效 |
| **MAD 得分爆炸与方向误判** | CPU 使用率得分 189.9σ，网络 IO 得分 125.1σ，Top3 根因全被平稳指标霸占；压测时 CPU 飙高但方向显示“↓”；同一指标重复上榜 | 平稳指标 MAD 接近 0，微小波动产生极高 z-score；原方向判断仅对比最后一点与全局中位数，压测后回落导致误判；多模板映射同一指标导致重复添加 | 引入 95 分位数替代 max 去毛刺、分数封顶（30σ）、基线 MAD 下限过滤、相对波动阈值校验（min_relative_mad）；方向改为前 70% 基线 vs 后 30% 异常区间均值对比；用 `seen_metrics` 字典按指标名去重保留最高分 |
| **近零基线指标直接弃权** | MySQL 慢查询数、连接数等指标基线中位数为 0，`mad_score` 直接返回 0，无法参与根因排名 | 原有逻辑对 `median == 0` 的处理过于严格，未考虑“从零突增”的异常场景 | 仅当 `baseline_mad < 1e-9`（完全静止）时才返回 0；近零基线仍允许正常计算 z-score，捕获从无到有的突变异常 |
| **测试流程与系统协同缺陷** | 单独进行 `stress` 压测，但 ES 无对应时间段日志，`aggregation` 为空，根因分析无触发入口；动态窗口与固定窗口同时输出造成混淆 | 日志生成器未与压测同步运行；原设计同时返回两套窗口，违反单一职责原则 | 确保日志生成器持续运行，压测后等待 Filebeat 采集完再执行巡检；仅保留基于真实异常时间的动态根因分析，去掉固定窗口冗余查询 |
| **crontab执行失败** | crontab脚本执行失败，手动执行正常 | crontab缺少工作目录、Python/conda环境变量 | 所有路径使用绝对路径；直接调用虚拟环境内Python可执行文件；脚本头部补充PATH |
|**Ollama开启GPU加速时CUDA内核报错、程序闪退崩溃**|启动ollama serve直接闪退，抛出0xc0000409内存异常；显卡环境无法正常加载模型，CPU模式却可以正常运行|本机CUDA版本和Ollama内置cuda推理库版本不匹配|指定适配的CUDA推理库`OLLAMA_LLM_LIBRARY=cuda_v11`；安装对应版本显卡驱动，成功启用GPU推理|
| **Windows‑Ollama CUDA程序崩溃** | Ollama服务闪退、栈溢出、CUDA报错 | Windows端显卡环境和推理库存在兼容问题，GUI不会读取临时环境变量 | cmd命令行手动配置环境变量启动serve；按需切换cuda_v11推理库 |
| **模型首次加载速度缓慢** | 首次接口调用延迟三十秒以上 | 闲置之后Ollama自动卸载模型，下次请求需要重新载入权重 | 配置环境变量 OLLAMA_KEEP_ALIVE=24h，实现模型常驻内存 |
| **LLM接口调用超时阻塞** | 巡检调度脚本卡住，告警推送中断 | requests请求没有设置超时，大模型推理缓慢时程序无限阻塞 | http请求添加 timeout=60，超时之后直接推送原始日志告警 |
| **Prompt过长返回格式混乱** | 大模型输出文本杂乱、JSON格式错乱 | 1.5B小模型上下文容量有限，冗余提示词干扰输出 | 精简Prompt，只传入日志、得分等关键字段，强制约束返回格式 |
